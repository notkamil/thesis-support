# Методология бенчмарков

Сценарии (что мерим) описаны в [`scenarios.md`](scenarios.md). Этот документ — короткая справка о том, **как** мы это мерим: контракт сборки, поток данных, инструменты, статистика, контроль шума, протокол прогона.

## 1. Контракт сборки

Бенчи измеряют те числа, которые увидит **внешний пользователь** при подключении наших крейтов и линковке против `libotterbrix.so`. Поэтому:

- bench-проект — **отдельный** Cargo workspace в `benchmarks/`, без path-зависимостей наружу. Исходники четырёх крейтов (`otterbrix-sys`, `otterbrix`, `seaorm-otterbrix`, `sqlx-otterbrix`) подтягиваются через `git clone` нашего форка по `DEFAULT_REV` из [`benchmarks.config`](benchmarks.config);
- C-бенчи — **отдельный** скрипт [`code/c/build.sh`](code/c/build.sh), линкуется к `libotterbrix.so` через `-L $DIST/lib -Wl,-rpath,$DIST/lib`. Не подключён к cmake-tree otterbrix; не требует conan. Используется собственный pure-C прокси-заголовок [`code/c/include/otterbrix_capi.h`](code/c/include/otterbrix_capi.h) (повторяет публичный C-ABI без C++-only `<cstdint>`/`<cstdlib>`);
- сама `libotterbrix.so` собирается **один раз** скриптом [`scripts/bootstrap.sh`](scripts/bootstrap.sh) и кладётся в `.workdir/dist/<sha>/{lib,include}/` вместе с `manifest.json`. Симлинк `.workdir/dist/current → <sha>` — стабильный путь, на который смотрят и `.cargo/config.toml`, и `code/c/build.sh`. `bootstrap.sh` идемпотентен; `--rebuild` форсирует пересборку, `--local-source <path>` берёт исходники из локального checkout (но ставит `dirty: 1` в манифесте — публиковать такие числа нельзя).

## 2. Поток данных

1. Каждый бенч-бинарник выполняет операцию N итераций.
2. Каждая итерация дампится в **сырой CSV** одной колонкой `ns` (одно число на строку). Никакая статистика на этом этапе не считается.
3. CSV складываются в `results/raw/` (для финального прогона — в `results/<timestamp>_<host>_<sha>/raw/`); один CSV на пару `(scenario, layer)`, для сценариев с вариантами — суффикс `_n100` / `_k1000` / `_sum`.
4. [`scripts/analyze.py`](scripts/analyze.py) читает все CSV, считает статистику, строит графики. Промежуточная сводка — [`scripts/quick_summary.py`](scripts/quick_summary.py) (медиана, p95, Δ% от sys в одной markdown-таблице).

Сырые CSV — первичный артефакт; всё, что приведено в ВКР, выводимо из них одним запуском `analyze.py`.

## 3. Инструменты

Никаких benchmarking-фреймворков (`criterion`, Google Benchmark) — каждый бенч это **минимальный самодостаточный исполняемый файл**, который сам делает setup, warmup и замер. Это убирает риск «фреймворк измеряет своё».

- **Rust** — индивидуальные бинарники [`code/rust/src/bin/sN_*_<layer>.rs`](code/rust/src/bin/), один файл = один сценарий × один слой. Замер — `std::time::Instant::now()` (`clock_gettime(CLOCK_MONOTONIC)`).
- **C** — индивидуальные [`code/c/src/sN_*.c`](code/c/src/), один файл на сценарий. Замер — тот же `clock_gettime(CLOCK_MONOTONIC)` через хелпер `bench_now_ns()`.

Слои, конфигурация движка и флаги сборки — в [`scenarios.md`](scenarios.md). **Входные данные** во всех слоях побайтно одинаковые: детерминированный поток `rand_chacha::ChaCha8Rng` с фиксированным seed'ом. Rust-бенчи зовут [`bench_rows()`](code/rust/src/data.rs)/`lookup_ids()` напрямую; C-бенчи читают тот же байтовый поток из `data/rows_max.bin` / `data/lookup_ids_max.bin`, которые однократно дампит [`gen_bench_data`](code/rust/src/bin/gen_bench_data.rs) (`cargo run --release --bin gen_bench_data`).

## 4. Статистика

Все процедуры реализованы в [`scripts/analyze.py`](scripts/analyze.py).

- **Медиана** как центральная мера. Не среднее: распределения тяжелохвостые и часто бимодальные.
- **95 % CI медианы** — bootstrap с `B = 100 000` ресэмплами; границы — 2.5 / 97.5 перцентили распределения медиан. Не предполагает нормальности.
- **Хвост** — `p95`, `p99`, `p999`. Для коротких операций именно хвост определяет SLO.
- **Сравнение слоёв** — bootstrap на разности медиан `median(layer) − median(c)`; если 95 % CI разности накрывает ноль — оверхед статистически незначим.
- **Шум** — coefficient of variation (`std/mean`); CV > 5 % помечает прогон как шумный.

## 5. Контроль шума

Финальный прогон выполняется на выделенной машине (Selectel) при следующих обязательных настройках:

- turbo boost — off (иначе частота гуляет в 2× между измерениями);
- scaling governor — `performance` (`cpupower frequency-set -g performance`);
- HyperThreading — off (BIOS или `echo off > /sys/devices/system/cpu/smt/control`);
- бенч прибит к выделенным физическим ядрам через `taskset -c 2,3`;
- swap не активен (`free -h` по строке `Swap` показывает `0`);
- бинарники не пересобираются между прогонами слоёв одного сценария (иначе теряется L1i/uop-кеш).

[`scripts/run.sh`](scripts/run.sh) проверяет эти условия на старте и **отказывается** запускать бенчи, если хоть одно нарушено. Локальный smoke на ноутбуке проверки пропускает, но его числа в ВКР не идут.

## 6. Протокол прогона

1. Зафиксировать SHA в `benchmarks.config` (`DEFAULT_REV=<short-sha>`).
2. На дедик-машине: `git clone … benchmarks && cd benchmarks`.
3. `./scripts/bootstrap.sh` — собирает `libotterbrix.so` и пишет manifest.
4. `cargo run --release --bin gen_bench_data` (из `code/rust/`) — однократно дампит детерминированные датасеты в `data/`.
5. `./scripts/run.sh --check` — собирает бенчи и проверяет настройки шума.
6. `./scripts/run.sh --full` — гонит все 12 сценариев на 5 слоях; CSV в `results/<timestamp>_<host>_<sha>/raw/`.
7. `./scripts/analyze.py results/<timestamp>_<host>_<sha>/` — статистика и графики.
8. Серия повторяется **трижды** (`_run1` / `_run2` / `_run3`); порог стабильности — медианы между прогонами расходятся не более чем на 5 %. В ВКР идут числа из `_run1`, стабильность фиксируется одной строкой в приложении.

Полный прогон занимает порядка часа, тройной — около трёх.

## 7. Что мы сознательно не делаем

- **Не делаем C++-baseline.** Все Rust-слои и C-bench выходят на движок через одни и те же `extern "C"` точки `libotterbrix.so` (которые внутри идут в `wrapper_dispatcher_t::execute_sql_with_params` / `create_database` / ...). Между ними разница — это ровно то, что мы и хотим измерить (overhead биндингов). C-ABI shim (`string_view → std::string`, `sql_param_t → pair<...,logical_value_t>`, `cursor_storage_t`) присутствует одинаково во всех слоях и в относительных сравнениях сокращается. C++-bench разделил бы константу на «движок» и «обёртку» — это интересно мейнтейнерам otterbrix, но не отвечает на наш вопрос. Если защитный комитет попросит — добавим один sanity-bench на C++ через `add_subdirectory` в otterbrix-дереве (≈30 минут работы).
- **Не считаем `mean ± 1.96·std/√n`** и **не сравниваем средние** — формула предполагает нормальность, средние сильно перекошены выбросами. Только медиана + bootstrap.
- **Не отбрасываем выбросы.** Каждая итерация в CSV «как есть»; их вклад уходит в `p99`/`p999`, не в медиану.
- **Не публикуем числа с дев-машины.** Только дедик с активным шумовым контролем.
- **Не мерим конкуррентные сценарии.** `Database` — `Send`, не `Sync`; адаптеры сериализуют доступ через `Arc<Mutex<_>>`; числа говорили бы больше про мьютекс, чем про обёртку.
- **Не мерим в режиме `wal_on=true`/`disk_on=true`.** Шум диска доминирует над FFI-эффектом и обесценивает KPI «оверхед ≤ 10–20 %». Реалистичный режим оговаривается абзацем в ВКР.
